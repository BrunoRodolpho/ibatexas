

# ===== RESEARCH: google =====

## summary
As of June 2026, Google's agent stack centers on ADK 2.0 (GA at I/O '26, May 19): a code-first framework in Python, TypeScript, Go, Java, Kotlin (docs moved to adk.dev) with LlmAgent + Sequential/Parallel/Loop workflow agents, a new graph-based Workflow Runtime, collaborative agent modes (chat/task/single-turn), sub_agents/AgentTool composition, MCP/OpenAPI/function tools, and Runner/SessionService runtime. Its evaluation story is the most mature part: two-axis evaluation (tool-call trajectory vs final response) over .test.json (unit) and .evalset.json (multi-turn integration) files, ~10 built-in metrics mixing deterministic (tool_trajectory_avg_score, ROUGE response_match_score) and LLM-judge criteria (final_response_match_v2, rubric-based, hallucinations_v1, safety_v1, multi_turn_*), thresholds in test_config.json, executed via pytest (await AgentEvaluator.evaluate(...)), adk eval CLI, or adk web UI. LLM-driven user simulation (ConversationScenario: starting_prompt + conversation_plan + user_persona with EXPERT/NOVICE/EVALUATOR personas) replaces scripted multi-turn tests, currently limited to reference-free criteria. A2A v1.0 (Linux Foundation, 150+ orgs, SDKs in 5 languages, production at Microsoft/AWS/Salesforce/SAP/ServiceNow) defines AgentCard discovery (signed, .well-known), Task lifecycle (SUBMITTED/WORKING/INPUT_REQUIRED/AUTH_REQUIRED/COMPLETED/FAILED/REJECTED), Message/Part/Artifact over JSON-RPC, gRPC, or REST+SSE. Vertex AI was rebranded Gemini Enterprise Agent Platform at Next '26 (absorbing Agentspace); its managed Agent Engine/Runtime provides Sessions + Memory Bank (GA, LLM-consolidated cross-session memories), Example Store (preview, dynamic few-shot retrieval), Code Execution sandbox, OTel-based Cloud Trace observability, online eval monitors, Agent Gateway/Identity governance, and the new Managed Agents/Interactions APIs. Eval tooling remains Python-only; ADK-JS (@google/adk) lacks AgentEvaluator.

## applicability
- Evalset file convention transfers directly: adopt ADK's two-tier split (.test.json single-session unit cases, .evalset.json multi-turn integration cases) as JSON fixtures in adjudicate's conformance suite and claustrum. Field shape — conversation[] of {user_content, final_response, intermediate_data.tool_uses, session_input} — maps onto claustrum's perceive->...->act loop where intermediate_data.tool_uses becomes the expected IntentEnvelope/tool-call sequence and session_input seeds SessionPort state.
- Two-axis evaluation (trajectory vs final response) with per-metric thresholds in a config file is the key pattern: build a Vitest helper mirroring `await AgentEvaluator.evaluate(agentModule, evalsetPath)` that runs claustrum's loop against fixtures and asserts tool_trajectory_avg_score-style exact match on adjudicate verdicts/tool calls (deterministic, threshold 1.0) while using LLM-judge or ROUGE-style scoring only for ResponderPort/synthesize text (threshold ~0.8). Since adjudicate is a deterministic kernel, its verdict trajectory (EXECUTE/REFUSE/DEFER/...) is even more exactly assertable than ADK tool trajectories.
- ADK's metric taxonomy is a ready-made checklist for the conformance suite: add rubric_based_tool_use_quality, hallucination-groundedness (vs GroundingPort context), safety, and multi_turn_task_success analogs. Vertex's trajectory_precision/trajectory_recall/in-order/any-order variants are trivial pure functions over tool-call arrays — implement in TypeScript in the conformance package, no Google dependency.
- User simulation is the highest-value transfer for ibatexas: extend adjudicate's `scenarios generate` and `red-team` CLI commands with ADK's ConversationScenario shape {starting_prompt, conversation_plan, user_persona} and an LLM-driven UserSimulator (configurable model, max_allowed_invocations cap, Jinja-like template overrides). Personas map to Brazilian food-commerce users: novice WhatsApp customer, PIX-payment-confused buyer, adversarial refund-seeker. Follow Google's constraint: simulated conversations pair with reference-free criteria (safety, hallucination, goal-completion) not exact response matching.
- Persona-with-violation-rubrics pattern (EXPERT/NOVICE/EVALUATOR + custom rubrics) plugs into red-team: define personas whose rubric violations (e.g., agent reveals another customer's order, executes payment without REQUEST_CONFIRMATION) are scored per-turn — this is precisely an adjudicate PolicyBundle assertion expressed as eval criteria.
- ADK's safety layering validates adjudicate's architecture and suggests one addition: Google scatters policy across before_tool_callback, in-tool guardrails, and runner-level plugins; adjudicate centralizes it in the kernel (better auditability). Worth borrowing: runner-level plugin stages orthogonal to verdict guards — PII redaction and input/output screening as interceptors in claustrum's submit/act phases, plus a cheap-model-as-judge screen (their Gemini Flash Lite pattern) before expensive adjudication.
- A2A Task lifecycle states map almost 1:1 onto adjudicate verdicts: REQUEST_CONFIRMATION≈INPUT_REQUIRED, ESCALATE≈AUTH_REQUIRED, REFUSE≈REJECTED, DEFER≈WORKING(async), EXECUTE→COMPLETED. Aligning claustrum's HandoffPort state machine with these names/semantics costs nothing and makes future A2A interop (or exposing ibatexas agents to partners) a thin adapter; official A2A JS SDK exists if needed.
- A2A AgentCard pattern: publish a signed capability manifest per ibatexas tool pack (skills, securitySchemes, capabilities) — even consumed only internally over NATS, it gives the 17 tools a discoverable, verifiable contract; DataPart is the natural carrier for IntentEnvelope JSON in any cross-agent message.
- Memory Bank's design — LLM-consolidated cross-session memories generated from session event logs, with memory profiles, revision history, and scoped retrieval — is a blueprint for a claustrum MemoryPort backend on Postgres(+pgvector)/Redis sourced from SessionPort events; revision inspection aligns with adjudicate's audit-ledger ethos. Their Sessions/MemoryBank split (raw per-conversation events vs derived long-term memories) is the right storage boundary.
- Example Store = claustrum's FewShotIndex port, validated: the transferable insight is the continuous-improvement loop — harvest production interactions (especially eval failures and ESCALATE/REWRITE cases from the audit ledger) into the few-shot store so retrieval improves the agent without retraining.
- Observability convergence: Google standardized on OpenTelemetry for agent traces (ADK --otel_to_cloud, Unified Trace Viewer showing reasoning steps), confirming adjudicate's OTLP package direction. Transferable feature: link every failed eval case to its OTLP trace ID; claustrum's content-addressed prompt graphs + LLM trace replay already exceed ADK's replay story — keep that as a differentiator.
- Adopt Google's four-layer testing pyramid for ibatexas: (1) interactive eval authoring in the operator console — add 'save this session as eval case' from audit-ledger replay, mirroring adk web's record-conversation-to-evalset and threshold sliders; (2) evalset runs in Vitest/CI; (3) simulated-user multi-turn suites nightly; (4) online monitors with quality alerts off OTLP metrics and sampled NATS events in production.
- Strategic gap/opportunity: ADK TypeScript (@google/adk) exists but its evaluation framework (AgentEvaluator, adk eval, user simulation) is Python-only as of June 2026. There is no dominant TS-native agent-eval framework — adjudicate's conformance suite + CLI (simulate/red-team/replay/scenarios generate) can adopt ADK's proven file formats and metric names for familiarity while remaining the TS-native solution; avoid adopting ADK itself since claustrum already covers the runtime role.
- ADK 2.0's graph workflows with a determinism slider (model-led to strict) echo claustrum's PlannerPort/ResolverPort split; their collaborative-agent return modes (chat=manual return, task=auto-return with clarifications, single-turn=agent-as-tool) are a useful taxonomy for HandoffPort semantics between pack agents (e.g., pack-orders delegating to pack-payments as 'task', not 'chat').

## findings
- **ADK 2.0 GA (I/O 2026)**: Shipped May 19, 2026. Adds graph-based Workflow Runtime (slider from model-led to deterministic), collaborative agents with three modes — chat (handoff, manual return), task (clarifications allowed, auto-return), single-turn (agent-as-tool, parallel) — dynamic workflows via Python decorators, ADK Kotlin beta, and ADK for Android with on-device Gemini Nano. Five language SDKs: Python, TypeScript, Go, Java, Kotlin. Docs relocated from google.github.io/adk-docs to adk.dev. [https://cloud.google.com/blog/topics/developers-practitioners/io26-news-for-agent-developers-on-google-cloud]
- **ADK core architecture**: LlmAgent plus template workflow agents (Sequential, Parallel, Loop) and custom agents; composition via sub_agents, agent transfer, and AgentTool. Runtime: Runner, SessionService (state/history), Artifacts, Memory, plus automatic context management (filtering, summarization, lazy-loading). Tools: function tools, OpenAPI specs, MCP, built-ins (Google Search etc.), tool action-confirmation. Deploys to Agent Runtime (Agent Platform), Cloud Run, GKE. [https://adk.dev/]
- **ADK evalset file format**: Two tiers: .test.json (single-session, unit-test style) and .evalset.json (multi-session, multi-turn integration). Fields: eval_set_id, eval_cases[], conversation[] turns with user_content, final_response (expected), intermediate_data.tool_uses (expected tool trajectory), intermediate_data.intermediate_responses (sub-agent outputs), session_input (app_name, user_id, initial state). Pydantic-backed schema; AgentEvaluator.migrate_eval_data_to_new_schema converts legacy files. [https://adk.dev/evaluate/]
- **ADK evaluation metrics**: Built-in criteria: tool_trajectory_avg_score (exact tool-call sequence match, default threshold 1.0), response_match_score (ROUGE-1 vs reference, default 0.8), final_response_match_v2 (LLM-judge semantic equivalence), rubric_based_final_response_quality_v1, rubric_based_tool_use_quality_v1, hallucinations_v1 (groundedness), safety_v1, multi_turn_task_success_v1, multi_turn_trajectory_quality_v1, multi_turn_tool_use_quality_v1. Thresholds set in test_config.json under "criteria". [https://adk.dev/evaluate/criteria/]
- **AgentEvaluator + pytest integration**: Programmatic runs inside pytest: `await AgentEvaluator.evaluate(agent_module=..., eval_dataset_file_path_or_dir=...)`. ADK 1.17+ unified the evaluate() API (replacing Evaluator(...).evaluate(...).eval_results[0]). Philosophy: probabilistic agents make deterministic pass/fail assertions unsuitable; evaluate both decision trajectory and final output quality against thresholds. [https://adk.dev/evaluate/]
- **ADK eval execution surfaces**: Three modes: (1) adk web UI — record live conversations as eval cases, edit them, threshold sliders per metric, side-by-side failure comparison, Trace tab for execution flow; (2) adk eval CLI: `adk eval <agent> <evalset> --config_file_path --print_detailed_results`, with case filtering `file.json:eval_1,eval_2`; (3) pytest via AgentEvaluator for CI. [https://adk.dev/evaluate/]
- **ADK user simulation**: UserSimulator: an LLM plays the user. ConversationScenario = {starting_prompt, conversation_plan (natural-language goals), user_persona}. Prebuilt personas EXPERT/NOVICE/EVALUATOR differ on proactive detail, question scope, error correction; custom personas support violation rubrics. UserSimulatorConfig: model (default gemini-flash-latest), max_allowed_invocations, custom_instructions (Jinja). Currently compatible only with reference-free criteria: hallucinations_v1, safety_v1. Added via `adk eval_set add_eval_case --scenarios_file`. [https://adk.dev/evaluate/user-sim/]
- **A2A protocol status/adoption**: Donated to Linux Foundation June 2025; at one-year mark (April 9, 2026): 150+ organizations, 22,000+ GitHub stars, SDKs in Python, JavaScript, Java, Go, .NET; production use at Microsoft, AWS, Salesforce, SAP, ServiceNow across supply chain, financial services, insurance, IT ops. v1.0 (early 2026) made it production-grade; signed Agent Cards verify domain ownership; protocol now at v1.2 under Agentic AI Foundation governance. [https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year]
- **A2A message format (v1.0 spec)**: Three bindings: JSON-RPC 2.0, gRPC, HTTP+JSON REST (SSE streaming). AgentCard: provider, capabilities (streaming, pushNotifications), skills, securitySchemes (OAuth2, mTLS, API key), SHA-256 signed, discovered at .well-known/a2a-agent-card. Task states: SUBMITTED→WORKING→COMPLETED/FAILED/CANCELED/REJECTED, with INPUT_REQUIRED and AUTH_REQUIRED interrupts. Message {role, parts[], contextId, taskId, referenceTaskIds}; Parts: TextPart, FilePart (raw/url+mediaType), DataPart (structured JSON). Artifacts hold task outputs. Webhook push-notification configs; A2A-Version header. [https://a2a-protocol.org/latest/specification/]
- **Vertex AI → Gemini Enterprise Agent Platform**: At Cloud Next 2026 Google rebranded Vertex AI as Gemini Enterprise Agent Platform and absorbed Agentspace into the unified Gemini Enterprise product. Components: Gemini Enterprise app (end users), Model Garden (200+ models incl. Anthropic Claude), governance plane (Agent Identity, Registry, Gateway), and dev tools from no-code Agent Designer/Workspace Studio up to ADK. Agent Gallery surfaces partner agents (Adobe, Salesforce, ServiceNow, Workday) from Marketplace. [https://cloud.google.com/blog/products/ai-machine-learning/the-new-gemini-enterprise-one-platform-for-agent-development]
- **Agent Engine / Agent Runtime model**: Fully managed runtime deploying agents from ADK, LangChain, LangGraph, AG2, LlamaIndex, or custom code without infrastructure management. Capabilities: Sessions (per-conversation state), Memory Bank, Example Store, Code Execution sandbox, multi-region deployment, VPC/Private Service Connect, IAM agent identity, Agent Gateway for governed access. Evaluation features: agent evaluation, offline/online monitors, quality alerts, prompt optimization. [https://docs.cloud.google.com/vertex-ai/generative-ai/docs/agent-engine/overview]
- **Sessions + Memory Bank**: Both GA, billed separately from Jan 28, 2026 ($0.25 per 1,000 stored session events or memories). Sessions hold one conversation's events; Memory Bank consumes stored sessions to generate consolidated cross-session memories (LLM extraction + ingestion + consolidation), with memory profiles, revision inspection, scoped retrieval, and ADK integration via MemoryService/quickstarts. [https://docs.cloud.google.com/vertex-ai/generative-ai/docs/agent-engine/memory-bank/overview]
- **Example Store**: Preview feature under 'continuous quality improvement': store and dynamically retrieve few-shot examples at runtime to improve agent performance; examples can be uploaded from production interactions, closing the loop between observed failures and prompt-level fixes. [https://docs.cloud.google.com/vertex-ai/generative-ai/docs/agent-engine/overview]
- **Observability/tracing**: ADK 1.17+ ships native OpenTelemetry export to Google Cloud Observability (--otel_to_cloud flag). Agent Engine integrates Cloud Trace (OTel-based), Cloud Logging, Cloud Monitoring, and a Unified Trace Viewer exposing agent reasoning steps for debugging. Trace logging is positioned as the substrate for continuous optimization. [https://futureagi.com/blog/evaluate-google-adk-agents/]
- **Vertex Gen AI evaluation service (agent metrics)**: SDK-level agent evaluation independent of ADK: one call triggers agent execution and computes trajectory metrics — trajectory_exact_match, trajectory_in_order_match, trajectory_any_order_match, trajectory_precision, trajectory_recall — plus final-response metrics (LLM autoraters). Docs current as of June 2026 under Gemini Enterprise Agent Platform. [https://cloud.google.com/vertex-ai/generative-ai/docs/models/evaluation-agents]
- **Google's recommended agent testing methodology**: Layered: (1) interactive vibe-checks in adk web, capturing sessions as eval cases; (2) file-based evalsets with deterministic trajectory + LLM-judged response metrics in pytest/CI; (3) LLM user simulation with personas for multi-turn robustness; (4) production online monitors, quality alerts, and prompt optimization in Agent Engine. I/O '26 'Evaluation Suite' bundles synthetic user simulation, multi-turn testing, and LLM autoraters; Agents CLI adds eval/deploy/observability skills. [https://developers.googleblog.com/announcing-user-simulation-in-adk-evaluation/]
- **ADK safety/guardrail patterns**: Agent-auth vs user-auth tool identity; in-tool guardrails via Tool Context policies (deterministic constraints e.g. allowed tables); before_model_callback/before_tool_callback validating params against state for policy enforcement; runner-level plugins: Gemini-as-Judge input/output screening (Gemini Flash Lite), Model Armor plugin, PII redaction plugin; sandboxed hermetic code execution; VPC-SC perimeters; UI escaping of model output. [https://adk.dev/safety/]
- **ADK for TypeScript (@google/adk)**: npm @google/adk + @google/adk-devtools (devtools v1.2.0, June 3, 2026). Zod v3/v4 tool schemas with type inference; Node + browser, ESM/CJS; sequential/parallel/loop/routed workflows; A2A remote-agent delegation; built-in Google Search/Maps/Vertex AI Search tools; CLI: adk create/run/web/deploy cloud_run; deployment-agnostic. Notable gap: AgentEvaluator/adk eval framework not present in JS repo — evaluation remains Python-only. [https://github.com/google/adk-js]
- **Managed Agents API (I/O '26)**: New agent-as-a-service rung: Managed Agents API with Interactions API for invocation, Google Cloud Sandbox (ephemeral secure execution), MCP server support. Plus Skill Registry (public preview) for centralized domain-logic reuse, and Antigravity 2.0 desktop/CLI/SDK for multi-agent orchestration; platform explicitly interoperates with external coding agents including Claude Code. [https://cloud.google.com/blog/topics/developers-practitioners/io26-news-for-agent-developers-on-google-cloud]

## findings
- **Claude Agent SDK — packages and positioning**: @anthropic-ai/claude-agent-sdk (npm, bundles native Claude Code binary) and claude-agent-sdk (PyPI, Python 3.10+). query()/ClaudeSDKClient run the full Claude Code agent loop in-process with built-in tools: Read, Write, Edit, Bash, Monitor, Glob, Grep, WebSearch, WebFetch, AskUserQuestion. Auth via ANTHROPIC_API_KEY, Bedrock, Vertex, Azure, Claude Platform on AWS. From June 15, 2026, SDK/claude -p usage on subscription plans draws a separate monthly Agent SDK credit. [https://code.claude.com/docs/en/agent-sdk/overview]
- **Agent SDK permission system**: Six modes: default, dontAsk (deny instead of prompt — for headless CI), acceptEdits, bypassPermissions, plan, auto (TS-only model classifier). Evaluation order: hooks → deny rules → ask rules → mode → allow rules → canUseTool callback. allowed_tools/disallowed_tools support patterns like Bash(rm *) and mcp__server__* globs. setPermissionMode() switches mid-session. Subagents inherit bypassPermissions/acceptEdits/auto from parent, non-overridable. [https://code.claude.com/docs/en/agent-sdk/permissions]
- **Agent SDK hooks**: Callback hooks at lifecycle points: PreToolUse, PostToolUse, Stop, SessionStart, SessionEnd, UserPromptSubmit, and more. HookMatcher(matcher="Edit|Write", hooks=[fn]) pattern. Hooks can validate, log, block, or transform tool calls; a PreToolUse hook can deny a call outright, and hooks still execute under bypassPermissions. Primary interception point for external policy engines. [https://code.claude.com/docs/en/agent-sdk/hooks]
- **Agent SDK subagents**: agents option takes named AgentDefinition objects (description, prompt, tools[], optional model). Invoked via the Agent tool (include "Agent" in allowedTools to auto-approve). Each subagent gets its own context window and narrower toolset; messages from subagent context carry parent_tool_use_id for per-subagent tracking — usable for fan-out fleets. [https://code.claude.com/docs/en/agent-sdk/subagents]
- **Agent SDK sessions**: Session id arrives in the init SystemMessage; options.resume=session_id continues with full context, and sessions can be forked to explore alternate branches. Session state is JSONL on your filesystem (vs Anthropic-hosted event log in Managed Agents), enabling replay/diffing of agent transcripts. [https://code.claude.com/docs/en/agent-sdk/sessions]
- **Agent SDK — MCP, skills, plugins, settings**: mcp_servers option attaches stdio (command/args, e.g. npx @playwright/mcp) or remote MCP servers; tools surface as mcp__server__tool. SDK also loads Claude Code filesystem config: .claude/skills/*/SKILL.md, .claude/commands, CLAUDE.md, and programmatic plugins (bundle skills+agents+hooks+MCP). settingSources restricts which config sources load — key for hermetic CI harnesses. [https://code.claude.com/docs/en/agent-sdk/mcp]

# ===== RESEARCH: agentTesting =====

## summary
Mid-2026 practice has converged on simulation-based testing for conversational agents: a user-simulator LLM + tool environment + judge, graded primarily by comparing final environment/DB state to an annotated goal state (tau-bench/tau2-bench), with pass^k (all k trials succeed; p^k decays exponentially — 90% pass@1 ≈ 57% at k=8) as the reliability gate for customer-facing flows. tau3-bench (Mar 2026) added RAG-knowledge and full-duplex voice domains. TypeScript-native harnesses exist: LangWatch Scenario (@langwatch/scenario v0.4.13, vitest/jest, UserSimulatorAgent/JudgeAgent/RedTeamAgent, script DSL with mid-conversation assertions, deterministic caching) and LangSmith openevals runMultiturnSimulation (simulated users, per-example persona prompts, stopping conditions, trajectory evaluators). Anthropic's eval guidance codifies grader taxonomy (code-based > model-based > human), clean-environment-per-trial isolation, grade-outcome-not-path, 20–50 tasks from real failures, and transcript reading. Browser QA products bifurcated: managed code-generation (QA Wolf), intent-locator platforms (Momentic: cache-and-revalidate, cached steps +52ms vs Playwright, >99% steps deterministic), OSS hybrids (Stagehand v3 CDP/self-healing, Passmark flow-cache with zero-LLM replay, Vercel Agent-Browser, Expect, Shortest). Conversational-simulation platforms: Coval, LivePerson, Maxim, Braintrust. Consensus best practices: deterministic assertions first, LLM-judge as supplement never sole merge gate; cached/replayed simulations on PR, live-LLM pass^k runs nightly; ephemeral seeded environments (Neon branches/Testcontainers, idempotent factories, tagged teardown); evaluate both trajectory and outcome; permanent hybrid pyramid — scripted tests keep money math/compliance/backend, agentic simulations cover high-churn multi-turn journeys, never wholesale replacement.

## applicability
- Harness skeleton: adopt @langwatch/scenario (TypeScript, vitest-native — ibatexas already uses Vitest) as the simulation runner. Wrap claustrum's cognitive loop in an AgentAdapter whose call(input) feeds perceive→…→act and returns the synthesized reply; UserSimulatorAgent plays the WhatsApp customer (pt-BR personas: order, amend, cancel, PIX hesitancy); JudgeAgent rubrics plus custom assertion functions in the script DSL give deterministic mid-conversation checks. # ===== RESEARCH: managedAgents =====

## summary
By mid-2026, server-side managed agents converge on a standard shape: durable-execution runtime (Temporal, Inngest, Restate, Hatchet) journaling every LLM/tool step so crashes resume mid-run instead of restarting; event-driven triggering where dormant agents wake on bus events (NATS JetStream work-queue streams with durable pull consumers is the canonical pattern); human-in-the-loop as first-class suspension (signals/waitForEvent/awakeables) consuming zero compute for days; and managed deployment planes (LangSmith Deployment, OpenAI AgentKit, AWS Bedrock AgentCore microVMs, Cloudflare Durable-Object agents). Versioning treats prompts/agents like deployable software: immutable versions, 24h shadow runs with LLM-judge diffing, 1-5% sticky canaries, automated rollback on refusal-rate/latency/cost deltas. Budget enforcement sits outside agent code at the gateway/runtime: per-session token budgets, fleet ceilings, hard kill switches before the next API call, plus approval-gate maturity ladders (draft-only -> approve -> auto-under-threshold). Failure handling combines idempotency keys derived from runId+stepId, effectively-once side effects via intent ledgers ("late-bound saga" pattern: intent write -> execute -> result write), and saga compensation registries for partial multi-step failures. MCP (tools) + A2A (agent-to-agent, now Linux Foundation AAIF) is the consensus service interface. Consensus guidance: most systems should be deterministic workflows; use an agent only when the decision cannot be captured in if/else. The user's adjudicate kernel already implements the rarest pieces (intent ledger, intentHash effectively-once, DEFER/REQUEST_CONFIRMATION, audit, replay); the genuine gaps are step-journaled resumability of claustrum's loop, durable timers/wake-on-event for parked runs, NATS trigger layer with ack-after-commit, rollout controller, run-level budget metering, compensation registry, and MCP/A2A facade.

## applicability
- Adjudicate already IS the 'late-bound saga' intent ledger: IntentEnvelope persisted before execution, intentHash dedup = effectively-once, audit ledger = result journal. The genuinely missing half is the OTHER bracket: step-journaled resumability of claustrum's cognitive loop. A crash mid perceive->...->act today loses in-flight run state. Add a run journal (Postgres table: runId, stepIdx, portName, inputHash, persisted output) so ModelProvider/tool calls replay from cache on resume — Restate's ctx.run()/Hatchet durable-task semantics implemented over the existing Postgres, or adopt an engine.
- Engine choice for the TS/pnpm/Postgres/Redis/NATS stack: Hatchet fits best (TypeScript SDK, Postgres-only dependency matching the existing audit-ledger DB, easy self-host); Restate is the lightweight alternative with virtual objects mapping cleanly to per-conversation SessionPort state; Temporal TS SDK is the proven heavyweight (signals -> REQUEST_CONFIRMATION resolution, durable timers -> DEFER deadlines, continue-as-new -> long WhatsApp conversations) but adds a cluster; Inngest overlaps most with what adjudicate+NATS already provide (its waitForEvent ~= the existing approval-engine), so it adds least.
- DEFER (park/resume) and REQUEST_CONFIRMATION half-solve HITL, but lack durable timers and zero-process suspension: parked intents need scheduled wake (timeout -> ESCALATE or expiry), and resume must rehydrate a claustrum run purely from persisted journal + session state with no in-memory continuation. This is the single biggest gap versus Temporal/Restate-class runtimes.
- NATS trigger layer for ibatexas: JetStream stream per domain (orders, payments, whatsapp) with WorkQueuePolicy + durable pull consumers per agent pack; agents dormant until order.created / pix.payment.received / whatsapp.message.in. Dedup via Nats-Msg-Id on publish + intentHash at the kernel; ack only AFTER the run-journal/audit-ledger commit (ack-after-commit) so redelivery is safe. Fan-out one event to multiple packs via separate consumers. This makes agents 'server-resident triggered' without an always-running process per agent.
- Versioning: claustrum's content-addressed prompt graphs already give immutable versions (better than most 2026 registries). Missing is the rollout controller: a version registry binding (promptGraphHash, PolicyBundle version, model id) into named 'assistant' versions (LangGraph-style); shadow runs by replaying production traffic through candidates using the existing CLI replay + LLM trace replay (no user impact, double token cost); tenant- or percentage-based sticky canaries; automated rollback triggered by adjudication-decision deltas (REFUSE/ESCALATE/REWRITE rate shifts are a ready-made, stack-native canary metric no one else has).
- Version pinning of in-flight runs is required once runs are durable: a run started on prompt-graph v3 / PolicyBundle v7 must complete on those versions (Temporal worker-versioning analog). Content-addressing makes this trivial — store hashes in the run journal and resolve by hash on resume.
- Budgets: adjudicate guards decide per-intent but nothing enforces run/tenant-level spend outside agent code. Add a budget meter at the ModelProvider port boundary (Redis INCR counters: tokens+cost per runId, tenant, day) checked synchronously before each LLM call; surface budget state into the IntentEnvelope so a PolicyBundle guard can REFUSE/ESCALATE over-budget actions; iteration cap on the cognitive loop with cap-hit -> ESCALATE; fleet ceiling + kill switch via a NATS control subject that revokes runs before the next call. The autonomy ladder (draft-only -> approve -> auto-under-threshold) maps directly onto REQUEST_CONFIRMATION thresholds per tool in PolicyBundle, e.g. PIX refund limits.
- Agent-as-a-service facade: expose ibatexas pack tools (17 LLM-callable tools) via an MCP server package (they are already MCP-shaped: name/schema/handler), and expose claustrum agents via A2A agent cards where A2A task states map onto kernel decisions (input-required ≈ REQUEST_CONFIRMATION, working ≈ DEFER-resumed, rejected ≈ REFUSE). This makes the stack consumable by external orchestrators without bypassing adjudication.
- Compensation: intentHash dedup prevents duplicates but nothing undoes partial multi-intent plans (CreateOrder ok, PIX charge fails -> orphan order). Add a compensation registry per tool pack (each tool optionally declares an idempotent compensating tool); on plan failure, claustrum emits compensating IntentEnvelopes in reverse order — compensations themselves flow through adjudicate, keeping undo auditable. Propagate idempotency keys (runId+stepIdx) into Medusa and PIX provider calls.
- Retry policy nuance for the loop: transport/429 errors -> retry the activity; schema-invalid tool calls -> re-plan (feed the error back through PlannerPort), never blind-retry; REFUSE from adjudicate -> re-plan or synthesize refusal, not retry. Encode this taxonomy in the runtime, not prompts.
- Agent/workflow boundary for ibatexas: keep PIX webhook processing, order state transitions, reservation confirmations as deterministic NATS handlers (no LLM); reserve the claustrum loop for ambiguous natural-language input (WhatsApp) and exception handling. The stack's architecture (deterministic kernel adjudicating LLM proposals) already embodies the 2026 'hybrid' consensus — the discipline is refusing to route deterministic events through the LLM loop at all.
- Net gap list for server-resident triggered agents: (1) step-journaled resumable cognitive loop; (2) durable timers + zero-process suspension for DEFER/confirmation; (3) JetStream trigger layer with ack-after-commit; (4) rollout controller (shadow/canary over prompt graphs + PolicyBundles with decision-rate rollback triggers); (5) run/tenant budget metering with external kill switch; (6) compensation registry; (7) MCP/A2A facade; (8) in-flight version pinning. Items already solved by adjudicate and NOT to rebuild: intent ledger, effectively-once execution, approval gates, audit, replay tooling.

## findings
- **Why durable execution for LLM agents**: Temporal records every workflow step as immutable event history; a process dying at step 47 of 100 replays the log and resumes at 48. Long-running agents fail constantly because frameworks treat LLM calls as fire-and-forget. Resuming saves token cost (LLM results cached, never re-bought). Feb 2026: Temporal raised $300M Series D at $5B; OpenAI, Replit, Lovable, ADP (HITL agents), Abridge build agents on it. [https://effloow.com/articles/temporal-ai-agents-durable-execution-guide-2026]
- **Temporal architecture mapping for agents**: Deterministic workflow code coordinates non-deterministic activities: LLM calls, tool calls, API requests go in activities (retried automatically); sequencing/control flow in workflow. Signals enable HITL approval; workflows hold state for years; continue-as-new handles unbounded agent loops. OpenAI Agents SDK integration GA March 23, 2026 (Python); TS, Go, Java, .NET, Ruby SDKs exist; Vercel AI SDK plugin adds durability behind familiar code. [https://temporal.io/blog/announcing-openai-agents-sdk-integration]
- **Inngest AgentKit**: TypeScript-first library: Agents composed into Networks with shared State and deterministic state-based Routers. step.ai wraps inference with auto-retry and result caching for durability. MCP servers usable as tools. Providers: OpenAI, Anthropic, Gemini, Grok. step.waitForEvent() pauses for approvals hours/days with no polling. Event-triggered functions; open-source self-hostable runtime; pricing per step/event can scale unpredictably. useAgent React hook streams durable backend runs to frontend. [https://agentkit.inngest.com/overview]
- **Restate durable agents**: Lightweight runtime journaling every step via ctx.run(); crash -> replay journal, skip completed steps, resume exactly where left off. TypeScript SDK plus Vercel AI integration (durableCalls() middleware persists model responses); Python integrations: OpenAI Agents, Google ADK, Pydantic AI, LangChain. Durable sessions via embedded K/V (virtual objects) with concurrency management; resilient human approvals lasting minutes or months; strong serverless support. [https://docs.restate.dev/ai/patterns/durable-agents]
- **Hatchet**: Orchestration engine for background tasks, AI agents, durable workflows. Uses Postgres as the durability layer for runtime and observability, so self-hosting is simple. Durable tasks checkpoint agent state and resume after failure. Python, TypeScript, Go, Ruby SDKs. Billions of tasks/month in production; 10k+ OSS deploys/month plus Hatchet Cloud. Companion repo 'durable-execution-the-hard-way' shows building the engine on plain Postgres. [https://github.com/hatchet-dev/hatchet]
- **Event-driven agent triggering on NATS**: 2026 pattern: agents subscribe to event streams and stay dormant at zero cost until a trigger. Fan-out: one event (e.g. asset.updated) simultaneously wakes multiple specialized agents. NATS JetStream adds durability, acks, replay; WorkQueuePolicy streams + durable pull consumers give exactly-once consumption and horizontal scaling; pull consumers recommended for new projects. Synadia positions NATS as the substrate for distributed agent infrastructure (RethinkConn 2026 workshop). [https://fast.io/resources/ai-agent-event-driven-architecture/]
- **JetStream for AI workloads**: Synadia's reference: JetStream as durable low-latency work queue decoupling bursty traffic from inference capacity across regions; enables scale-to-zero, multi-region failover, per-function isolation. Dedup via Nats-Msg-Id; explicit acks let consumers ack only after downstream commit, giving at-least-once with idempotent processing. [https://www.synadia.com/blog/scaling-global-ai-inference-with-nats-jetstream]
- **LangGraph Platform / LangSmith Deployment**: Renamed LangSmith Deployment (Oct 2025). Runs long-running stateful agents with task queues, horizontal scaling, cross-thread persistence. 'Assistants' = versioned configurations of one agent graph, enabling version management/reuse. Deployment modes: Cloud SaaS, Hybrid (SaaS control plane + self-hosted data plane), fully self-hosted (free Developer tier to 100k node executions/month; Plus $0.001/node + $0.0036/min standby). [https://www.langchain.com/blog/langgraph-platform-ga]
- **OpenAI AgentKit + cloud deployment models**: OpenAI AgentKit (Oct 2025): visual Agent Builder with guardrail nodes, ChatKit embedding, Evals; Workflows API and ChatGPT deployment planned; April 2026 SDK update added sandboxed computer environments. AWS Bedrock AgentCore (GA evolution, April 2026 Managed Harness): define agent via model+prompt+tools, per-session isolated microVM, CPU billing stops during I/O wait, 8-hour sessions, framework-agnostic (LangGraph, CrewAI, OpenAI SDK, Strands). [https://aws.amazon.com/blogs/aws/introducing-amazon-bedrock-agentcore-securely-deploy-and-operate-ai-agents-at-any-scale/]
- **Cloudflare Agents SDK**: Each agent instance is a Durable Object with its own SQLite DB; state persists across requests and hibernation; agents hibernate idle and wake on demand ('millions of agents, costing nothing when inactive'). Built-in scheduling, realtime, MCP, workflows. 2026 additions: keepAlive() (March), Project Think fibers (runFiber, stash, onFiberRecovered) for durable execution after eviction. The hibernate/wake model is the serverless analog of event-triggered server-resident agents. [https://developers.cloudflare.com/agents/]
- **Prompt/agent versioning pipeline**: 2026 standard pipeline: PR -> CI types+unit -> offline evals on golden set -> 24h shadow -> 5% canary A/B -> 100% ramp, old version kept warm for one-command rollback. Prompt updates drive most LLM production incidents (Deepchecks), so prompt changes get the same rails as code deploys. Agent versioning treats 'intelligence as deployable software' with explicit rollback and lifecycle management. [https://tianpan.co/blog/2026-03-13-prompt-versioning-change-management-production]
- **Shadow and canary mechanics**: Shadow: duplicate production traffic to candidate (never user-facing), compare via LLM-judge on task completion/accuracy/format, plus token-cost and latency diffs; doubles inference spend temporarily. Canary: 1%->5%->20%->50%->100%, session-sticky routing required; monitor p95/p99 latency, refusal rate, cost/request, output-length distribution, regeneration/abandonment. Automated rollback triggers, e.g. p99 +40%, refusal +5%, cost delta over budget — no human required. Also: tool-call pattern analysis (order, skipped/extra tools) as canary eval. [https://tianpan.co/blog/2026-04-09-llm-gradual-rollout-shadow-canary-ab-testing]
- **Budget enforcement architecture**: Enforcement must sit outside agent code, intercepting before each API call ('agents rationalize away prompt-based constraints'). Levels: per-session token budgets (would have capped a $47k incident), per-agent-type fleet ceilings detecting anomalies ($0.50/run agent suddenly $50x1000), per-tenant/daily caps via virtual keys. Hard stops terminate sessions non-negotiably; soft triggers escalate to human review or cheaper-model routing. Kill switch revokes execution before the next call, without agent acknowledgment. [https://waxell.ai/blog/ai-agent-token-budget-enforcement]
- **Approval gates and autonomy ladder**: Enterprise rollout ladder: launch draft-only -> execute-with-approval -> execute automatically under thresholds (e.g. refunds under $50 auto, >$200 require approval). Control-plane parameter checks: agent purchase $600 vs $500 autonomous limit -> reject or route to human. Iteration kill-switches via turn caps, budget monitors, automated context trimming prevent runaway loops. [https://atlan.com/know/ai-agent-risks-guardrails/]
- **Agent-as-a-service via MCP + A2A**: Consensus: MCP = agent->tool capability access; A2A = agent->agent task negotiation/delegation across vendors/frameworks; complementary, not competing. Linux Foundation's Agentic AI Foundation (Dec 2025) now hosts both; 100+ enterprise supporters by Feb 2026; MCP at 97M monthly SDK downloads, adopted by Anthropic, OpenAI, Google, Microsoft, Amazon. Production pattern: each agent exposes skills via A2A agent card, internally reaches tools via MCP. Three-layer stack: MCP tools / A2A agents / WebMCP web. [https://www.xcapit.com/en/blog/agent-to-agent-protocols-mcp-a2a-2026]
- **Late-bound sagas / intent ledger pattern**: 'An agent is a saga the model writes as it runs, not a loop the model sits inside.' Runtime (not process) owns execution state. Per step: LLM proposes intent -> runtime persists intent to ledger -> worker executes -> result persisted -> LLM sees result. Bracket structure gives effectively-once side effects. Plus: zero-compute suspension (3-day human wait = database rows + webhook subscription) and out-of-band signals injecting cancellations/rate-limits without killing the workflow. [https://medium.com/agentspan/late-bound-sagas-why-your-agent-is-not-an-llm-in-a-loop-a8c50731c551]
- **Idempotency, retry vs re-plan, compensation**: Idempotency keys derived from workflowId+stepId for non-idempotent tool calls. Key 2026 distinction: a malformed tool call is permanent at the call level but transient at the agent level — re-plan with the error in context, don't blind-retry. Hardest case is partial success (CreateOrder ok, ChargeCard fails): saga compensation pairs each step with an idempotent undo, run in reverse order. Airflow's AgentOperator durable=True replays cached steps with zero repeated LLM/tool calls. [https://www.motomtech.com/blog-post/ai-agent-retries-idempotency-tool-failures/]
- **When NOT to use an agent**: Most production AI systems should be workflows, not agents; most 'agent' use cases are workflows with an LLM in a step. Use an agent only when the decision cannot be captured in if/else logic, however complex; otherwise deterministic workflow is faster, cheaper, more reliable, debuggable. Documented anti-pattern: rebuilding workflows as autonomous agents -> 8x API cost, inconsistent outputs. 2026 play is hybrid: deterministic guardrails for reliability/auditability + LLM reasoning only for ambiguity. [https://www.aimadetools.com/blog/agent-vs-workflow/]
- **Durable-engine comparison frame**: Selection axes used in 2026 comparisons (Spheron, Hookdeck, Render): Temporal = heaviest, most proven, separate cluster, event-history replay with deterministic-code constraints; Inngest = event-native serverless functions, step-level durability, easiest DX; Restate = single lightweight binary, journal+virtual objects, best for serverless and per-entity sessions; Hatchet = Postgres-only dependency, queue+DAG+durable tasks, easiest self-host for teams already on Postgres. [https://www.spheron.network/blog/ai-agent-workflow-orchestration-temporal-inngest-restate-gpu-cloud/]
