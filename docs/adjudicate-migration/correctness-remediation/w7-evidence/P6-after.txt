── packages/tools/src/medusa/adjudicated.ts — wrapper extensions ───────────────
Added 2 new intent kinds (D10 EXCLUDED from KNOWN_INTENT_KINDS, per spec):
  - medusa.admin.order.edit.items.remove
      Rule: DELETE /admin/orders/:id/edits/:editId/items/:itemId
      Rationale: order.service.cancelItem() removes a single line from
      an in-flight order edit. The legacy pattern matched only the
      POST /edits/items shape (which Medusa actually exposes for ADD
      via that shape with body); the DELETE shape is editId-scoped.
  - medusa.admin.order.capture_payment
      Rule: POST /admin/orders/:id/capture-payment
      Rationale: order.service.capturePayment() triggers Medusa to
      mark the order as paid after the Stripe webhook confirms. No
      prior rule covered this path. Distinct from
      medusa.admin.order.update_metadata because the side-effect is
      payment-state, not just metadata.

Also added new PATH_RULE for the existing kind, to match the real shape:
  - POST /admin/orders/:id/edits/:editId/confirm → medusa.admin.order.edit.confirm
    (pre-existing rule matched /edits/confirm without :editId; that was
    never exercised by a real Medusa call. We keep both for resilience.)

KNOWN_INTENT_KINDS exclusion rationale (per D10):
  medusa.* kinds are wrapper-internal taxonomy keyed by HTTP method × URL
  shape. They are NEVER proposed by the LLM, NEVER appear on the
  CapabilityPlanner visibility list, and have no Pack association. The
  KNOWN_INTENT_KINDS allowlist in @ibatexas/llm-provider is for kinds the
  LLM may legitimately propose; medusa.* kinds are SYSTEM-actor-only
  egress kinds that bypass the LLM surface entirely. Registering them
  would expand the LLM's attack surface unnecessarily.
