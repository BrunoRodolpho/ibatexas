Bypass description (per W6 governance-coverage scan):
  Two adopter sites invoke `customerSvc.upsertFromPhone()` /
  `customerSvc.upsertFromWhatsApp()` directly, bypassing the kernel.
  Both are the ONLY path through which a new Customer row is ever
  created (post-OTP and pre-verified WhatsApp first-contact, respectively).

  Per CLAUDE.md rule #9 + pack-customer-onboarding §"customer.create",
  `customer.create` is a SYSTEM-only intent — only these two seed paths
  may emit it. There is already a `createFromEnvelope` method on
  customer.service.ts (line 272) that handles BOTH cases via the
  payload's `source` discriminator (`"otp"` vs `"wa-auto"`), but the
  call sites never invoke it.

Sites bypassing the kernel (BEFORE):
  - apps/api/src/routes/auth.ts:390
      const customer = await customerSvc.upsertFromPhone(phone, name ?? undefined)

  - apps/api/src/whatsapp/session.ts:135
      const customer = await customerSvc.upsertFromWhatsApp(phone)

Envelope method available on packages/domain/src/services/customer.service.ts:
  - createFromEnvelope (line 272) — accepts { phone, name? } in `extras`,
    branches on payload.source. For `wa-auto`, performs Prisma upsert
    with source: "whatsapp" + firstContactAt. For `otp` path, upserts
    with name. RETURNS the customer object {id} (or full row for OTP
    path).

Pack contract notes:
  - pack-customer-onboarding declares `customer.create` SYSTEM-only via
    `systemMinimum: "SYSTEM"` (types.ts:258-262). Envelopes must carry
    `taint: "SYSTEM"` and `actor.principal: "system"` to clear the gate.
  - Payload shape: { phoneHash: string, source: "otp" | "wa-auto" }
    — raw phone never enters policy state per PII discipline.
