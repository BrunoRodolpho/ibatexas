Symptom
-------
JWT cookies whose `sub` claim is the empty string would be assigned to
`request.customerId = ""`. Every downstream gate (`hasFreshOtp`,
`incrementOtpFailureCount`, `setCancelCooldown`, …) blindly built a
Redis key by string-interpolating `customerId`:

    rk(`anonymize:otp:${customerId}`)   →   "ibatexas:anonymize:otp:"
    rk(`anonymize:fail:${customerId}`)  →   "ibatexas:anonymize:fail:"
    rk(`anonymize:pending:${customerId}`) → "ibatexas:anonymize:pending:"

ALL customers with empty `sub` collapsed onto the same Redis namespace:

  - Attacker A's verified-otp marker enables Victim B's initiate-deletion.
  - Brute-force counter for one attacker locks out every other.
  - Pending-deletion receipt of one attacker overwrites another's.

The `requireAuth` upstream check (`if (!request.customerId)`) DID catch
empty strings (since `!""` is truthy), but defense-in-depth was absent:

  1. extractAuth assigned `request.customerId = ""` unconditionally —
     the only gate was the outer `!customerId` check, easy to skip in
     a future helper.
  2. Every otp-gate function assumed customerId was non-empty, with no
     explicit check.
  3. me.ts:364 used `request.customerId!` (non-null assertion) before
     hitting the gates.

Reproduction (showing the unguarded helper would silently build a
colliding Redis key):

    // pre-fix code path (extracted from git HEAD~1 of anonymize-otp-gate.ts):
    export async function markOtpFresh(customerId: string): Promise<void> {
      const redis = await getRedisClient();
      await redis.set(rk(`anonymize:otp:${customerId}`), "1", { EX: 300 });
    }

    // Calling: markOtpFresh("")
    // Redis state after: { "ibatexas:anonymize:otp:" → "1" }
    // ALL empty-sub customers now share the same marker.
